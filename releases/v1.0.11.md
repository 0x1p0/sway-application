# Sway 1.0.11

## A persistent app identity

Releases now use the same private app-signing identity, with the public certificate pinned in the release checks. Earlier ad-hoc builds identified each version by its executable hash; this change removes that source of repeated Accessibility permission loss.

**Upgrading from 1.0.10 or earlier may need one final permission grant.** If Sway appears enabled but gestures do not work, open System Settings → Privacy & Security → Accessibility, remove the old Sway entry, then add the copy in Applications and enable it. Return to Sway and choose **Check again**; quit and reopen once if macOS still reports the old state. The setup guide and settings now explain this recovery.

Subsequent releases keep the same bundle identifier and certificate requirement. This establishes identity continuity; it cannot override a user revocation, an OS policy change, or an administrator's restrictions. Sway never resets or grants permissions automatically. Keep the installed copy in Applications.

## Release safeguards

- Building, app signing, packaging, and update signing run on separate runners.
- App signing and publication each require release-environment approval.
- The packager cannot access either private key. Before publication, the ZIP must match the app signer's digest and the complete DMG app must match that ZIP.
- Two different universal test builds satisfy the same certificate requirement after their temporary signing keychains are deleted. Wrong signers, changed resources, and identifier-only signatures are rejected.

The app is **self-signed, not Developer ID signed or notarized**. The first-install warning remains. The certificate's public name is Sway; it contains no personal name or email. The existing update-signing key is unchanged. End-to-end Accessibility retention still needs an installed two-version test; signature tests do not modify anyone's permissions.
